# Migrations

Alembic, configured by `../alembic.ini` and `env.py`. The database URL comes from `DATABASE_URL`
(through `app.core.config.Settings`); it is never written into a file.

```bash
uv run alembic upgrade head        # apply
uv run alembic check               # fails if app/models and the migrations disagree
uv run alembic revision -m "..."   # new revision (hand-review every autogenerated diff)
```

- History is forward-only and is never restarted. Schema changes happen only here, never through
  `create_all()`.
- `v3_0001` is the first V3 revision. The Supabase inventory (2026-11-09) found no
  `alembic_version` table and none of the V2 tables, so the V2 revisions in `../legacy/alembic/`
  were never applied and are not carried over.
- Autogenerate compares only tables defined in `app.models`; the legacy Supabase tables
  (`contacts`, `projects`, `visits`, `customer`) are never proposed for dropping.
- Every new `public` table must enable row-level security and revoke the Supabase `anon` and
  `authenticated` default grants (see `v3_0001`), because the API is its only client.
- Integration tests run every revision against real PostgreSQL (`tests/test_migrations.py`).
